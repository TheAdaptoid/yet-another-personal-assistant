DETAIL

Code Comparison

How the streaming loop looks in each approach.

ChatService

class ChatService:
    def __init__(self, sessions, models, config):
        self._sessions = sessions
        self._models = models
        self._config = config

    async def stream(self, prompt):
        provider = self._models.get_provider(self._model)
        yield AgentStartEvent(self._model.id)
        async for delta in provider.invoke_stream(...):
            if delta.content:
                yield TextEvent(delta.content)
            if delta.reasoning:
                yield ReasoningEvent(delta.reasoning)
        yield AgentDoneEvent(content)

    save_session_after(response)

Orchestrator

class Orchestrator:
    def __init__(self, session_manager, stream_service,
                      prompt_builder, event_bus, config):
        self._sm = session_manager
        self._ss = stream_service
        self._pb = prompt_builder
        self._eb = event_bus
        self._config = config

    async def execute(self, prompt):
        messages = self._pb.build(...)
        self._eb.emit(AgentStartEvent(...))
        async for delta in self._ss.stream(messages):
            self._eb.emit(to_event(delta))
        self._sm.persist(messages + response)

Orchestrator overhead: PromptBuilder wraps a list concatenation. StreamService wraps provider.invoke_llm_stream(). EventBus.emit() adds indirection that Phase 1 doesn't need.

DECISION

Trade-off Matrix

Dimension ChatService Orchestrator
Onboarding One class to read, one flow to trace 5+ classes to understand first
Test complexity Mock 3 protocol deps, test one unit Mock 5+ deps, plus integration tests for Orchestrator
Phase 2: Tools Add ToolService dep to ChatService. Tool loop in one place. ToolService slots in as another sub-service. Clean.
Phase 3: Memory/MCP More deps on ChatService. Extract sub-services as needed. Add more sub-services. No refactor needed.
God class risk Medium — must actively extract as scope grows Low — orchestration is the only job
Over-engineering risk Low — right-sized for current needs High — 4 of 6 sub-services are thin wrappers
Iteration speed Change one file, test one file Change propagates across sub-services

ChatService wins on simplicity, iteration speed, and right-sizing.
The extraction to Orchestrator happens naturally when Phase 3 requires it.

STRATEGY

Evolution Path

Design extension hooks now. Ship the simplest thing. Extract when the weight justifies it.

Phase 1

ChatService owns the streaming loop and all 3 deps. No refactoring needed for Phase 2.

Phase 2

ToolService added as a 4th dep. ChatService routes tool calls through it. No structural refactor.

Phase 3

ChatService grows large. Extract into Orchestrator with specialized sub-services. Natural threshold.

DESIGN

Extension Hooks for Phase 2

ChatService is designed to accept extensions without changing its core loop.

class ChatService:
    def __init__(self,
        sessions: SessionService,
        models: ModelService,
        config: ConfigStore,
        tools: ToolService | None = None, # ← Phase 2: optional
    ):
        ...

    async def _tool_loop(self, messages): # ← Phase 2: added method
        if not self._tools:
            return messages
        # Execute tool calls, collect results, re-invoke

Optional deps. New services are None by default. Existing consumers don't change.

New methods, not new parameters. Tool loop is a private method called from within stream().

12 / 13
SUMMARY

Phase 1 Design Decisions

1

ChatService as coordinator

Single service with 3 protocol deps. Extracts to Orchestrator when scope demands it.

2

Protocol-based persistence

SessionStore / ConfigStore as protocols. Swap JSON for SQLite later by writing a new implementation.

3

Event-based streaming

stream() yields Event types using existing event model. WebSocket-ready from day one.

4

Optional extension hooks

ToolService and future services slot in as optional constructor deps. Core signature stays stable.

Services layer is the core. Everything else is a consumer.
